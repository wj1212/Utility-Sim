## Decisions taken

### The 2x2 is inside the utility agent, not against the baseline

The August deck described the ablation as "baseline vs curves-only" and "baseline vs
inertia-only", treating the threshold agent as the cell with neither mechanism. That is
wrong architecturally: the threshold agent does not score anything, and inertia is a
bonus added to a score, so there is nowhere to put it.

The four cells are therefore curve on/off by inertia on/off, all inside the utility
agent, with the threshold agent as an external reference that runs alongside in every
condition. Turning the curve off means clearing the curve list, which makes
`EvaluateCurve` fall back to `1 - value`, a linear mapping.

Two useful consequences. The ablation needs no new code at all, just different inspector
values. And at the current activation threshold both mappings put the intervention point
at need 0.29 to 0.30, so the agents stay matched across conditions without recalibration.

### Harmful switching is measured by how far the action got

"Interrupt count" conflates an agent that cannot make up its mind with one that
correctly leaves an action whose job is done. `AgentCore` now captures the abandoned
action's elapsed time and intended duration at the moment of interruption, since both
are overwritten as soon as the next pursuit begins. The ratio separates the two cases.

Checking this against the August data showed the contamination was confined to the old
configuration: with full restoration, 9 of 9 interruptions in one run were the agent
leaving a finished action; after partial restoration, 0 of 178 were.

### Outage rather than permanent removal

Permanently removing the fridge leaves only one option, so there is still nothing to
arbitrate. Removing it for a window and giving it back lets hunger fall far below the
threshold while it is gone, so the agent faces two urgent needs when it returns.

### Sweep the inertia strength

The 2x2 can only answer whether inertia helps. The deck promised tuning guidance, and
the March risk list named a specific failure mode for too much commitment. Sweeping the
bonus across five values turns a yes-or-no into a curve, and tests that prediction.

## What went wrong along the way

**Script execution order.** `AblationRunner` seeded the starting needs in `Start`, but
`AgentMetabolism` builds its need list in `Start` too and sets every value to 1. Order
between them is undefined, so the seeding was being overwritten on the first run. Fixed
by yielding a frame before touching agents.

**Console volume.** A full sweep produces roughly twenty thousand log lines, which slows
the editor and risks losing the batch. `AgentCore.VerboseLogging` is now a static switch
the runner turns off for the duration.

**A missing script warning on both agents** turned out to be `Agent_Baseline.prefab`
still referencing `AgentController`, the name `AgentCore` had before it was renamed.
Harmless, since the scene objects carry the real component, but worth clearing up.

## The finding, and how it changed during the day

The first pass through the 2x2 in the normal scenario looked like a clean result:
inertia reduced interruptions, the curve helped a little, the interaction was near zero.

Then a question about whether to add more agents to the scene led to measuring what the
two agents do to each other. The threshold agent is configured identically in all four
conditions and starts from identical seeded values, so any variation in its numbers is
interference. Median within-seed spread: **4.9 percentage points**.

The normal-scenario effects were +4.3 and -5.4. **Both sat inside the noise floor.** The
apparently clean result was not reportable.

What survived, and what the rest of the day was built on:

- Under outage the inertia effect is -51.4 pp, ten times the noise floor.
- Collapses go from 7 of 16 without inertia to 0 of 16 with, which is categorical and
  immune to this particular noise.
- The sweep found a minimum at bonus 0.30 and a rise by 0.50, worse in 7 of 8 seeds
  paired, +12.5 pp.

The right-hand side of that curve is the interesting part, because it is not intuitive:
more commitment produces *more* interruptions. The mechanism is visible in the data.

> **Retracted 27 October.** The "fifteen times" figure below is not reproducible;
> nothing in the repository computes it. The reproducible version of the same
> point is that the competing need has fallen to 0.19 before the agent switches
> at bonus 0.50, against 0.27 at 0.30. See `RESULTS.md` section 3.

Completion at abandon rises monotonically to 0.86, so the agent really is holding on
longer, and conflicts fall monotonically, so it is not indecision. But time spent below
0.15 after the resource returns is fifteen times higher at 0.5 than at 0.3. The agent
commits so hard that the other need is driven into crisis, and the crisis is what forces
the switch. Late, crisis-driven switching rather than early, indecisive switching.

Both failure modes named in the March deck now have data behind them.

## What this cost the August story

The 24% figure does not survive. Those eight repeats shared one starting state, so the
variation between them was frame timing rather than sampling. With eight genuinely
different starting states the normal-scenario difference disappears into the noise.

Worth reporting as a correction rather than hiding. The replacement claim holds across
starting conditions and says something the design literature does not.

## Three things found late in the evening

These came out of asking what a reader outside the project would actually want to know.
All three are in `RESULTS.md` as sections 6, 7 and 8.

**The threshold agent was sitting there unused.** It ran alongside the utility agent in
all 104 runs as a noise probe, and the question it answers was never asked: is utility
scoring worth the complexity over threshold rules? Normal scenario, the two are
indistinguishable, 2.1 against 2.3 interrupts per minute. Under outage the threshold
agent runs 13.2 and collapses in 13 of 32 runs, while the tuned utility agent stays at
2.3 and collapses in none. That is a better framing for the contribution than "how much
does each mechanism add", because the answer carries a condition: it depends on whether
the environment is going to change.

**Splitting the outage runs by phase inverted the story.** The assumption all day was
that removing the resource is the stress. Interruptions during the outage window are
**zero percent in every condition**. With one resource gone there is only one option, so
there is nothing to switch between. Everything happens after it returns, 92 to 93 percent
without inertia against 34 to 38 percent with it. Taking the resource away is not what
breaks the agent. Giving it back is. This also explains why permanent removal, considered
earlier in the day, would have shown nothing.

**A hypothesis for the null curve result, written down rather than tested.** With two
needs there is rarely a subtle ranking to make, because whichever need is lower is the
more urgent one and a straight line orders two values the same way a curve does. Curve
shape should only matter when several options score close together. Adding a third need
is the direct test, and it would serve the half of the title that currently has no
result. Not attempted today, and it should be raised with the advisor before being built.
