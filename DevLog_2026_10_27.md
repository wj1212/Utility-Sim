## The finding: the experiment minimised the effect it was looking for

The curve ablation has never produced a measurable effect. The standing explanation was
a hypothesis: with only two needs there is rarely a subtle ranking to make, so a straight
line orders two values the same way a curve does.

That may still be true. But there is a second reason, and unlike the first one it is
visible in the data.

**The two curve conditions were deliberately matched at the activation threshold.** Both
cross theta = 0.71 at need 0.29 to 0.30. This was a good decision when it was made: if
the two conditions started acting at different need levels, any difference would be
confounded with timing rather than shape.

Nobody then asked **where decisions actually happen**. Pooled over 3,972 logged decisions
in the normal scenario, the median need at decision time is **0.28**. The 25th percentile
is 0.11, the 75th is 0.49.

And at need 0.30, the tuned curve reads 0.71 while the straight line reads 0.70. **They
differ by 0.01.** Where they differ most, need 0.5 to 0.7 with a gap of 0.15, sits above
the 75th percentile.

> The two conditions were made nearly identical in the region where the agent operates,
> and then compared.

This reframes the null completely. It is not "the response curve does nothing". It is
"this experiment is not sensitive to the response curve, and here is the measurement that
shows why". That also makes it fixable, which the two-needs hypothesis did not.

Three fixes, cheapest first, now the closing beat of the talk:

1. Separate the two mappings across need 0.15 to 0.45, where decisions actually happen,
   rather than only at the tails. Rerun.
2. One agent per run. Seeding already pairs the conditions, so separate runs lose nothing
   and remove all 4.9 pp of interference.
3. A third need, to test whether shape starts to matter when several options score close
   together.

## Corrections to things already written down

### The curve's main effect is not inside the noise floor

`RESULTS.md` section 1 said both main effects in the calm scenario sit below the 4.9 pp
noise floor. Inertia's +4.3 does. The curve's is **-5.4**, which is larger. The sentence
was wrong on its face and would not have survived anyone doing the subtraction in the
meeting.

What the data supports is that neither effect can be **resolved** at this sample size.
The curve's effect runs the same direction in both scenarios, -5.4 calm and -3.6 under
outage, so it may well be real and small.

The headline is untouched. It rests on the collapse count, 5 of 16 against 0 of 16,
which is a count and immune to this particular noise.

### Adaptability was measured all along

`STATUS.md` had been saying the adaptability metric was never defined. That was wrong.

February defined it as "the time the agent survives without reaching a critical failure
state during these resource-scarcity tests". Checked against what exists:

| February asked for | what exists |
|---|---|
| a resource-scarcity test | the fridge removed for 60 s |
| a critical failure state | collapse, interrupt rate >= 80% |
| how often it is reached | 7/16 without inertia, 0/16 with |
| how long it stays in trouble | need level when it finally switches, 0.19 at beta 0.5 against 0.27 at 0.30 |

All four exist. It was measured and never labelled. The Fall plan is 4 of 4.

What genuinely cannot be measured as built is the specific idea floated to Amini in
August, "how long the agent keeps going to a resource that isn't there any more".
`ResourceOutage` calls `SetActive(false)` and `FindObjectsByType` skips inactive objects,
so the fridge leaves the agent's perception entirely and it never walks to a missing
object. Measuring that needs the object left visible with a dead affordance.

### The collapse threshold does not drive the result

80% is our own line, in our own invented term. Checked whether it matters:

| threshold | calm, no inertia | calm, inertia | outage, no inertia | outage, inertia |
|---|---|---|---|---|
| 70% | 5/16 | **0/16** | 13/16 | **0/16** |
| 80% | 5/16 | **0/16** | 7/16 | **0/16** |
| 90% | 4/16 | **0/16** | 3/16 | **0/16** |

The absolute counts move. The contrast does not: the inertia conditions never cross any
of the three lines, in either scenario.

## Two claims that should never have been made

**The code is not an advertisement system.** It was described as one, with the
`SmartObject` and `Affordance` types offered as proof. `Affordance.Amount` and
`.Duration` are read only by `AgentCore` at execution time; neither brain's `Decide()`
touches them. Scoring uses `TargetNeed` alone, to look up the agent's own need value.
Two food sources with different Amounts would score identically. The object is a passive
catalogue; all valuation is internal to the agent.

`DevLog_2026_01_31.md` had this right in January: broadcasting versus scanning, and
scanning deliberately chosen. The answer was in the repository and was not read before
contradicting it.

**No claims about how commercial games are implemented.** Not The Sims, not RimWorld. We
have read neither codebase. "Our implementation is scanning-based" is verifiable here;
anything about someone else's game is "what public descriptions say".

## About the talk

Four drafts. The first three were unusable for reasons worth recording.

**Draft 1** was written to a slide budget, 16 seconds and 60 characters per slide. That
stripped out rhythm and pushed toward claims the data did not support, including "it will
starve itself", which is false: `Mathf.Clamp01` holds needs at zero and nothing dies.

**Drafts 1 and 2** put threshold rules down to make utility scoring look better. That is
a bad posture and also inaccurate, since our own data has the threshold agent at 2.1
interrupts per minute against 2.3 in calm conditions. The current script presents them as
answering a different question.

**Drafts 1 to 3** were written in the wrong voice. `DevLog_2026_01_31.md` is the style
reference: flowing sentences, reasons given before conclusions, generous about other
people's work. The current draft follows it.

Settled: open on the problem rather than a personal anecdote, state the research question
inside the first 40 seconds, give the equation a beat of its own and use it to make the
ablation concrete, explain the metrics before the results, and close on three specific
fixes rather than a general plan.
